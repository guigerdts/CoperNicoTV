# E7-T9 — Compatibilidad general, diagnóstico y recuperación IPTV

Objetivo: auditoría integral del pipeline de reproducción y corrección de los problemas de compatibilidad en streams IPTV reales con una solución GENERAL, extensible y segura (no un parche para FX). Ampliar compatibilidad SIN regresiones en los canales que ya reproducen (HBO y Cinecanal HD: READY).

## Specs

- S1 (evidencia física). «E7-T8 ya está integrado y dispone de CI 5/5. Se confirmó reproducción real de: HBO: READY. Cinecanal HD: READY. Audio y vídeo funcionales. Canales problemáticos: FX, identificador 1274: ERROR_CODE_IO_UNSPECIFIED. IllegalArgumentException. ProgressiveMediaSource. HTTP no disponible. Fallo aproximadamente en 1 segundo. FX, identificador 1449: ERROR_CODE_PARSING_CONTAINER_UNSUPPORTED. UnrecognizedInputFormatException. ProgressiveMediaSource. HTTP no disponible. Fallo aproximadamente en 1 segundo. La lista contiene URLs Xtream y aproximadamente 146.000 entradas. Estos dos errores NO demuestran que ambos streams tengan la misma causa. No asumir que FX utiliza HLS, MPEG-TS u otro formato sin evidencia.»
- S2 (auditoría). «Realizar una auditoría integral del pipeline de reproducción de CoperNicoTV» inspeccionando «SesionMedia3.kt, Configuración de ExoPlayer, DefaultMediaSourceFactory, DefaultHttpDataSource.Factory, FuenteHttpSeguimiento, ResolverRedirecciones, Selección de MediaSource, Extractores disponibles, Manejo de MIME y extensiones, User-Agent, Headers HTTP, Gestión de credenciales, Ciclo de vida del reproductor, Diagnóstico y clasificación de excepciones, Selección de audio y subtítulos, Gestión de buffer y errores de reproducción.» «Antes de modificar código, reconstruir el flujo real desde la selección del canal hasta la primera muestra de vídeo.»
- S3 (detección). «Diseñar una estrategia de detección basada en evidencia combinada: 1. Metadatos M3U. 2. Extensión de URL. 3. Parámetros Xtream. 4. MIME de respuesta. 5. Redirecciones HTTP. 6. Inspección segura de bytes iniciales cuando corresponda. 7. Reconocimiento del contenedor. 8. Disponibilidad de extractores y módulos Media3.» Contemplar «MPEG-TS. HLS / M3U8. MP4 / fMP4. MPEG-DASH / MPD. AAC. MP3. Otros formatos que el stack actual pueda soportar realmente.» «No depender únicamente de la extensión de URL. No asumir que toda URL sin extensión es MPEG-TS. No asumir que toda respuesta HTTP 200 contiene vídeo. No confundir una respuesta HTML de autenticación o bloqueo con un stream válido.»
- S4 (MediaSource). «Implementar una selección explícita y verificable de MediaSource» evaluando «HlsMediaSource. ProgressiveMediaSource. DashMediaSource. DefaultMediaSourceFactory cuando su detección automática sea suficiente.» «Evitar crear una arquitectura paralela innecesaria si Media3 ya proporciona la funcionalidad requerida. …No implementar fallback indiscriminado que pruebe todos los MediaSource a ciegas. Si una estrategia falla, permitir una alternativa únicamente cuando exista evidencia de que el formato alternativo es plausible. Preservar los parámetros HTTP y la seguridad de las solicitudes.»
- S5 (diagnóstico). «Ampliar el diagnóstico para diferenciar: Fallo DNS. Conexión. Timeout. HTTP 3xx. HTTP 401/403/404/429/5xx. MIME inesperado. Respuesta HTML. Contenedor no reconocido. Extractor incompatible. Códec no soportado. Inicialización del decodificador. Fallo del renderer de audio. Fallo del renderer de vídeo. Error de configuración. Cancelación. Error de ciclo de vida.» Registrar «Canal. Identificador. Protocolo detectado. Formato esperado. Formato observado. MIME. MediaSource elegido. Extractor. HTTP inicial/final. Número de redirecciones. Esquemas inicial/final. User-Agent. Código Media3. Excepción original y causa raíz. Duración. Intentos y reintentos.» «Nunca incluir URLs completas, contraseñas, tokens ni credenciales en informes o logs.» «El diagnóstico debe diferenciar un error de red de uno de contenedor o decodificación.»
- S6 (seguridad HTTP). «Preservar E7-T8.» Auditar «Redirecciones HTTP ↔ HTTPS. Redirecciones cross-domain. No reenvío de credenciales entre dominios. Protección contra downgrade HTTPS → HTTP. TLS y validación de certificados. User-Agent. Headers específicos de cada fuente.» «No desactivar validaciones TLS. No enviar credenciales a dominios de destino no autorizados. No debilitar las políticas de seguridad para conseguir que un canal reproduzca.»
- S7 (recuperación). «Implementar recuperación selectiva. Reintentar errores transitorios de red. No reintentar indefinidamente errores HTTP definitivos. No repetir solicitudes por errores de contenedor sin una estrategia alternativa justificada. Diferenciar errores de inicialización y errores durante reproducción. Evitar bucles de reconstrucción del reproductor. Mantener la posición y el estado cuando una recuperación sea segura. Los reintentos deben ser acotados y observables.»
- S8 (pruebas). Matriz: «A. MPEG-TS válido. B. HLS válido. C. MP4 válido. D. DASH válido, si el módulo está disponible. E. URL sin extensión. F. Redirección HTTP → HTTPS. G. Redirección cross-domain. H. Respuesta HTML. I. HTTP 401. J. HTTP 403. K. HTTP 404. L. HTTP 302. M. Contenedor desconocido. N. MIME incorrecto. O. Error de decodificador. P. Timeout. Q. Cancelación durante preparación.» «Añadir pruebas de regresión para la configuración existente. No afirmar que un formato funciona si únicamente pasó un test unitario. Separar pruebas unitarias, instrumentadas y validación física. Los canales HBO y Cinecanal deben conservar su comportamiento.»
- S9 (restricciones). «No modificar el importador M3U. No modificar el cifrado ni las claves. No cambiar el formato de almacenamiento. No modificar Room. No introducir dependencias innecesarias. No reescribir el reproductor completo. No modificar contratos públicos sin justificación. No degradar TLS. No introducir URLs o listas de prueba externas como dependencia de producción. No declarar compatibilidad con códecs o protocolos que no estén soportados por el stack real.»
- S10 (ejecución). «No detenerse en una auditoría documental. Después de demostrar las causas, implementar las correcciones justificadas. Ejecutar tests, ktlint, detekt, instrumentados móviles y TV mediante CI. Corregir los defectos detectados y conseguir CI verde. …Si alguna hipótesis necesita evidencia física que no está disponible, dejarla identificada y preparar el diagnóstico necesario para medirla en el dispositivo.»
- S11 (entrega). Entregar «1. Causas raíz demostradas. 2. Arquitectura de detección y selección implementada. 3. Archivos modificados. 4. Pruebas nuevas y regresiones. 5. Resultados de CI. 6. - L2 (2026-11-15, T1 auditoría — flujo real y causas raíz con archivo y línea).
  - Flujo real (selección canal → primera muestra): `ReproductorViewModel.abrirSesion` (:341-381) crea `SesionMedia3(contexto, url, protocolo, preferencias, politica)`; el constructor construye `ExoPlayer.Builder.setMediaSourceFactory(FabricaMediaSourcesGrabadora(DefaultMediaSourceFactory(FabricaFuenteSeguimiento(trazadora)).setLoadErrorHandlingPolicy(...)))` (SesionMedia3.kt:77-86), `setMediaItem(mediaItemDe(url, protocolo))` + `prepare()` + `playWhenReady=true` (:141-143).
  - `mediaItemDe` (:475-482): declara `mimeType` SOLO si `mimeDeProtocolo(protocolo)` lo da (HLS→application/vnd.apple.mpegurl... en 1.5.0 APPLICATION_M3U8, DASH→APPLICATION_MPD, SMOOTH→APPLICATION_SS); PROGRESIVO → MediaItem SIN MIME.
  - Selección de MediaSource: `DefaultMediaSourceFactory` (Media3 1.5.0) resuelve por MIME del MediaItem; si es nulo, por la extensión del URI; si tampoco hay → `ProgressiveMediaSource` con `DefaultExtractorsFactory`. Consecuencia: **una URL Xtream sin extensión (caso FX) siempre cae a ProgressiveMediaSource** aunque el servidor sirva una lista HLS o HTML.
  - Clasificador de URL: `ClasificadorStream.clasificarHttp` (core/.../ProtocoloStream.kt:48-56) mira SOLO la extensión de la ruta (.m3u8/.mpd/.ism) — es la única señal de formato en todo el pipeline; no hay MIME de respuesta, ni sniffing, ni metadatos M3U en la selección.
  - **Causa raíz hipótesis FX 1449** (ERROR_CODE_PARSING_CONTAINER_UNSUPPORTED + UnrecognizedInputFormatException + ProgressiveMediaSource, fallo ~1 s, «HTTP no disponible» = sin estado HTTP en el diagnóstico): la respuesta HTTP 200 llegó (por eso no hay InvalidResponseCodeException) y NINGÚN extractor la reconoció. El caso típico: el servidor Xtream sirvió texto de lista HLS (#EXTM3U) o HTML de autenticación/bloqueo para una URL sin extensión → `TsExtractor`/extractores no la sniffean → `UnrecognizedInputFormatException`. Es una hipótesis de contenido; se demuestra con sniffing acotado de bytes iniciales (T2) y el diagnóstico ampliado (T3) que registrará el formato observado.
  - **Causa raíz FX 1274** (ERROR_CODE_IO_UNSPECIFIED + IllegalArgumentException, ~1 s, «HTTP no disponible»): la cadena de causas no fue un código HTTP; `IllegalArgumentException` en el camino IO no queda evidenciada por el diagnóstico actual. Requiere evidencia: la trazadora E7-T8 solo registra ante `InvalidResponseCodeException`; hay que registrar MIME/bytes/URI final también ante fallos no-HTTP (`HttpDataSourceException` con causa IllegalArgumentException) y diferenciarla (¿URL inválida? ¿redirección malformada? ¿argumento ilegal del extracto/factory?). T3 deja preparado el diagnóstico para medirla; no se asume la causa.
  - Hallazgo estructural: los fallos de parseo y de IO no-HTTP NO producen traza de red (TrazadoraRed solo ante InvalidResponseCodeException en FuenteHttpSeguimiento) → el diagnóstico de los dos canales FX carece de MIME/bytes/esquema final aunque la conexión llegue. Brecha de evidencia que T3 cierra.
  - Camino feliz a preservar (HBO/Cinecanal READY): mismo DefaultMediaSourceFactory + FabricaFuenteSeguimiento + cross-protocol redirects; CUALQUIER cambio debe dejarse como no-actuante cuando el formato declarado/observado ya funciona.
- L3 (2026-11-15, plan de arquitectura T2-T4 acordado con los specs).

Aciertos del camino actual: cero cambios.
